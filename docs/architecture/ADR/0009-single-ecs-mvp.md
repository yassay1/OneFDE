# 黑客松与MVP采用单台ECS一体化部署

状态：2026年11月4日用户明确确认单ECS方向；后续已授权并完成本地S1/S2适配和无模型验证，生产部署未实施。**MVP物理拓扑以本ADR取代ADR0003的专用执行主机要求及ADR0008的工程另机要求**；既有Run/权限/停止契约继续有效。

## 决定

一台阿里云x86 Linux ECS通过Docker Compose承载公司网站、内部工作台、FastAPI、PostgreSQL、可信Worker、四角色Runtime、按需OpenHands工程容器及客户最终产品。物理主机共享，服务身份、容器、目录、网络、资源和发布权限分开。先本地开发/验证，再经单独购买和部署授权实施。

Worker为独立常驻受信任进程，四角色按需加载，不为每个角色建常驻服务；Engineering工具在无Docker Socket的动态兄弟容器内执行。Worker可管理宿主Docker但不能给模型开放任意宿主命令。静态客户产品由Caddy直接服务，后端产品按需独立容器；工程提交与正式发布分开。

## 理由与代价

Compose明确支持单服务器生产部署；当前单创始人、一个工程活动Run和外部模型API，不需要默认第二台ECS、Kubernetes或Redis。物理分离是后续隔离/负载选项，不是当前可行性的前置条件。

接受同机内核、Docker管理面和故障范围共享的MVP约束；不宣称强敌对多租户隔离或高可用。先落实可信管理面、受限挂载/网络、create-time配额与备份恢复，再上线。Worker失陷的宿主权限风险保留，不能靠Socket只读挂载消除。

## 实施与重访

本地已实现`ecs_shared`、容器化可信Worker/SDK私网接线、创建时安全/限额及无模型standby；生产在线出口/每任务配额、网关/发布/备份仍未完成。不得设置旧专用节点确认开关冒充共享模式。未买机、未公网部署或调用模型。详细设计、资源估算和证据边界以[部署设计](../../operations/deployment.md)为唯一来源，[分阶段验收](../../operations/single-ecs-verification.md)通过后才记录对应能力完成。

实际资源争用、多个并发工程任务、客户隔离或可用性要求超出单机能力时，再将Worker+Sandbox优先迁出；不因角色数量自动拆机。研究依据见[调研记录](../single-ecs-research.md)。
