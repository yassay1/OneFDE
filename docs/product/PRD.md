# OneFDE 首版产品需求

版本为 0.7，状态为需求细化基线，技术推荐见架构文档，更新日期为 2026 年 11 月 4 日。本版按用户确认完整梳理四角色关系：Knowledge 同时支持 Business、FDE、Engineering，区分知识服务、持久能力资产和业务资料。具体技术配置与未决业务规则仍按各自确认状态维护。

方向依据见[产品定义基线](product-definition.md)。原始基线保持原样；本文件补充用户后续确认的模拟演示边界，细化当前版需求，不将候选技术写成既定方案。

## 产品目标与用户

OneFDE 服务创始人的内部经营和客户交付工作。首批服务对象是社区水果店和单体小型生鲜门店，客户使用公司交付的独立工具，首版不登录内部工作台。

首版要证明创始人能组织 Agent，将一项有证据的业务问题推进为真实软件交付，再将经过整理的能力用于第二次需求。成功依据是代码、检查、部署、反馈和复用记录，不能仅以聊天回答或页面数量代替。

目前没有试点门店与真实报价样例。因此先验证模拟案例中的工程闭环，真实业务效果、付费意愿和效率提升留待试点验证。

| 状态 | 本文件中的用法 |

已确认的方向包括内部 Web 工作台、四类 Agent 职责、Engagement 和 Capability Library、报价比较贯穿案例，以及真实软件生成与部署。无需为了比赛追求完美，优先完成范围清楚的小型交付闭环。

2026 年 11 月 4 日，用户认可进一步说明的协作原则：四角色共用执行框架，各自按职责配置上下文、工具和权限；FDE 组织客户交付，Backend 维护工作、权限、调度和状态；短查询/有界咨询直接调用，长期工作通过持续 Task 交接；业务问题、回答与范围内修改关联原 Task，多次 Run 可续作；工程提交由 FDE/创始人按证据评审，Knowledge 整理有来源的候选能力。Agent 按需运行，项目事实与代码持久保存。

后续澄清：模型尚未选定，平台需要支持兼容 API 的配置式接入，MiMo 不作为唯一厂商或固定型号。用户授权提出工程执行与部署推荐，尚无指定云平台或金额上限；这不表示任何候选组合已通过验证。

## 首版需求与完成条件

下表是需求细化。编号用于关联实施计划、测试和项目任务，不预定页面数量、组件或接口路径。

| 编号 | 所需行为 | 可观察的完成条件 |
| --- | --- | --- |
| P01 | Business 支持线索与销售准备 | 可整理线索、沟通证据和草案，向 Knowledge 查询获准案例/能力依据；公开表达不超出获准范围，交付背景关联 Engagement，模拟来源明确 |
| P02 | 创建并持续查看 Engagement | 客户或模拟身份、目标、证据、未知项、方案、任务、成果和反馈可关联查看；新会话可以依据项目记录继续工作 |
| P03 | FDE 先诊断再制定方案 | 方案说明问题、证据、规则确认状态、输入输出、范围和限制；关键未知项会提出具体问题，而非让工程 Agent 猜测 |
| P04 | FDE 检索能力并选择交付策略 | 在直接复用、组合扩展和局部开发间提出选择；记录选用能力版本、适用条件或未采用理由 |
| P05 | 将方案转成持续可管理的任务 | 关联 Engagement/原需求，明确负责人、执行者、范围、输入、前置产物与完成条件；同次交付可多轮修改，一个请求也可拆多个任务 |
| P06 | Engineering 真实执行工程 | 有真实文件修改、命令、构建/启动和核心检查结果；失败或受阻如实返回，执行进度与产物可关联任务 |
| P07 | 支持持续协作并区分执行与接受 | 后续输入和问题关联原 Task；标明已记录/已采用；待答后可新 Run 续作；工程提交经轻量业务评审后才完成 Task；重复、取消、失败和迟到结果可追溯 |
| P08 | 部署并记录交付 | 指定软件版本有实际可访问入口与访问检查；记录运行限制和使用方式；临时预览的生命周期不得被隐去 |
| P09 | 收集三角色反馈并整理候选资产 | Knowledge 接收 Business 的获准市场/销售反馈、FDE 的规则/方案/反馈和 Engineering 的实现/检查证据；整理保留来源/版本/条件，不将全部业务原文自动入库 |
| P10 | 支持经营、方案与工程复用 | 三角色均可检索获准资产或请求 Knowledge 分析；经营材料有可用依据，第二次方案/工程复用能指出固定版本、适配与重新检查证据 |

## 角色交接与人工参与

| 角色 | 输入与职责 | 应交出的内容 |
| --- | --- | --- |
| Business | 公司方向、获准市场/客户沟通记录、可公开案例与能力说明；经营研究、获客、材料和跟进，向 Knowledge 查询依据 | 有来源的线索、营销/销售草案、市场反馈；交付背景转 FDE，不自行承诺价格、合同或技术交付范围 |
| FDE | Engagement 证据/已确认规则、能力候选与知识支持；诊断、方案、复用取舍、客户工程组织和业务评审 | 有范围/完成条件的任务、业务答复及交付判断；获准结果回 Business，规则/方案反馈 Knowledge，重大取舍回创始人 |
| Engineering | 固定工程任务、授权样例/代码和获准知识支持；实现、调试、构建、检查和受控发布 | 代码/产物版本、真实检查和问题；业务不确定性回 FDE，实现/验证经验回 Knowledge，不接受自己的业务提交 |
| Knowledge | 三角色的具体咨询及获准经营/项目/工程来源；检索分析、解释比较、复用支持和候选资产维护 | 面向各请求方的有依据答复、候选资产/修订及来源/条件/验证限制；不代行经营决策、业务确认、工程检查或权限授予 |

创始人负责商业方向、报价合同、客户承诺、关键范围及发布权限的取舍。首版允许人工录入、触发和业务确认，四角色按需协作，不要求常驻自治运行；Engineering 的真实工程执行不能全部由人工手工完成来替代。

Knowledge 是横向支持角色，Business、FDE、Engineering 均可直接发起本职责范围内的咨询并回传反馈，不要求 FDE 逐次中转。简单检索可直接使用受控工具，需要解释/比较/整理时调用 Knowledge；工程中的客户规则或范围不确定性仍回 FDE。

Capability Library 保存经整理的可复用知识/模块/经验及版本。业务资料保存经营记录、Engagement、原始客户证据和业务状态，仍归对应业务对象维护；Knowledge 可按有效授权读取这些来源，不把原文或每次答复自动复制成通用资产。资料范围、来源证据和公开用途的权威约定见[能力库约定](../../capability-library/README.md)。服务三个角色不意味着三者可见同样资料，Knowledge 的服务账号也不扩大请求方权限。

## 六组角色关系检查

| 关系 | 正向交接与返回 | 责任边界 |
| --- | --- | --- |
| Business ↔ FDE | 线索/沟通证据/可行性请求 → 诊断与方案依据、获准交付摘要 → 销售跟进及新需求反馈 | 商业承诺由创始人确认，客户工程由 FDE 组织 |
| FDE ↔ Engineering | 明确工程 Task/规则/验收条件 → 业务问题或工程提交 → 答复、采用修改与评审 | 持续工作不靠会话常驻；Engineering 不自行改业务规则或自验收 |
| Business ↔ Knowledge | 案例/服务能力/行业与材料依据请求 → 可用于指定用途的有来源答复；市场/销售反馈回传 | 内部可见、可复用与可公开分别核查；不把推测或试验包装成商业承诺 |
| FDE ↔ Knowledge | 方案/业务知识/复用适用性请求 → 条件、候选比较与限制；规则/方案反馈回传 | FDE 负责项目判断，Knowledge 不替客户确认事实 |
| Engineering ↔ Knowledge | 模块/接口/依赖/兼容与工程经验请求 → 版本/实现/检查依据；实现和验证反馈回传 | 工程咨询可直接进行，实际集成和检查仍由 Engineering 负责 |
| Business ↔ Engineering | 按授权引用或核查工程产物中的技术事实，获准结果可用于材料 | 不设销售直接修改客户工程的默认通道；涉及客户方案、开发/部署工作经 FDE 和 Task 授权 |

六组关系覆盖不等于六组都要常驻互调。Founder 可直接给各角色目标或作关键决定；短咨询记录工作归属，长期独立工作走统一任务协议，确认、发布、公开用途和状态写入仍由程序约束。

## 从请求到结果

普通请求先关联经营场景或指定 Engagement。FDE 整理证据和方案，检索能力，形成明确任务。Engineering 在任务边界内执行，回传产物和检查；FDE 解释业务结果与剩余问题。交付和反馈后，Knowledge 整理候选资产，供后续项目检索和复用。

对已有工作的补充应关联原任务；新的交付范围单独记录。信息不足时展示具体待确认问题；工程失败与等待业务确认应能区分。重试保留历史结果，不能覆盖掉失败依据。运行结束、任务完成和 Engagement 已交付不是同一含义。

推荐将同次未关闭交付的补充、问题与回答保存在 TaskInput；待采用的输入不等于当前 Run 已读取。工程需要答复时保存现场并结束本轮执行，回答采用后在原 Task 下创建新 Run。工程提交进入轻量 review，由 FDE/创始人按明确版本与证据接受或要求修改。Task 接受不等于客户已验收，也不自动授予生产发布权限；不建设正式审批流程。

短期检索与有界专业咨询可直接调用工具或角色能力；需要独立交付、异步等待或恢复的工作使用 Task。Business 与 FDE 可双向交接，Engineering 的业务问题回 FDE；问题默认留在原 Task，不为每次答复再派一个子任务。已关闭任务的后续工作建立有关联的新 Task，避免一个开发任务无限覆盖全部维护。

推荐采用“FDE 语义协调加程序 Coordinator”：FDE 负责诊断、复用取舍和任务拆分，程序层负责项目范围、去重、依赖、运行状态和结果归属。Coordinator 不是第五个 LLM Agent。Task/Run 与 Session 分离，首版一个活动工程 Run；状态、持久化和执行器以架构和数据模型为准，尚未实现。

## 首个模拟案例

场景和规则的维护位置为[报价比较演示记录](../../engagements/demo-supplier-quotes/brief.md)，以下只列边界摘要。

用户已确认第一轮最小比较范围：只比较商品、等级和规格明确一致且单位可换算的报价；缺失信息标记待核对；暂不计算运费、起订量和送货条件。结果需说明它比较的是约定口径下的报价，不代表全部采购成本或采购决策。

输入优先为 Excel/CSV，输出包含可比较项、不可比较或待核对项及其原因。需要结果展示和必要导出；导出格式、Excel 版本兼容、字段映射和具体换算表尚待细化。

## 首版非目标

首版不建设客户登录内部工作台、完整 CRM/ERP、多门店管理、独立 QA Agent、复杂审批或正式客户验收工作流。也不包括微信群自动读取、图片语音报价识别、自动询价下单、完整采购库存财务系统，以及无人监督的商业决策。

不设置独立 QA Agent 仍需要完成构建、启动和核心功能检查；不建设审批系统仍需要明确实际执行与发布权限。
