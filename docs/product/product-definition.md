# 1. 产品概述

## 1.1 公司定位

我们要经营一家面向生鲜行业商家的 AI 技术解决方案公司。

公司以 OPC（One-Person
Company，一人公司）的方式运营，由创始人主导经营和关键决策，借助 MiMo
Agent
团队完成市场研究、客户开发、业务诊断、软件开发、部署交付和经验沉淀。

公司向客户提供的不是一个通用 AI
聊天工具，而是能够解决具体经营问题的技术服务与成果，例如：

-   面向实际业务的小型软件和工具；
-   自动化工作流；
-   AI Agent 及其业务集成；
-   现有工具或系统的改造、连接与扩展；
-   后续的功能迭代和技术服务。

客户提出经营问题，公司负责理解业务、设计方案并交付可使用的解决方案。

## 1.2 OneFDE 产品定位

**OneFDE 是 OPC 内部使用的经营与工程交付平台。**

它帮助一个人组织 Agent
团队完成公司经营和客户项目交付，将客户的模糊经营问题转化为明确方案、可运行的软件和可复用的业务能力。

OneFDE 不是首阶段直接销售给水果店老板的 SaaS
产品。客户购买的是公司交付的软件、自动化工作流或 AI 解决方案；OneFDE
是公司内部用于生产和交付这些成果的平台。

## 1.3 核心价值

OneFDE 需要解决三个层次的问题：

1.  **让一个人能经营公司**：辅助市场研究、客户线索挖掘、营销和销售跟进。
2.  **让一个人能完成技术交付**：将业务诊断、方案制定、工程执行和部署连接起来。
3.  **让每次交付都积累能力**：将经过整理的行业知识、业务模块和工程经验沉淀到能力库，支持下一次复用。

核心价值不是 Agent 数量，而是一个人能否借助 Agent
团队持续获得客户、完成真实交付，并逐渐降低重复交付成本。

# 2. 目标客户与市场切入

## 2.1 首批目标客户

**首批聚焦社区水果店、单体小型生鲜门店。**

选择这类客户的主要考虑：

-   老板通常直接参与日常经营，需求沟通和试点决策链条相对短；
-   日常工作中存在订单整理、供应商报价、采购数据处理等重复任务；
-   很多场景可以先通过 Excel、CSV
    或文本资料验证价值，不必一开始接入复杂业务系统；
-   可以从范围清晰的小工具开始，逐步了解真实经营流程。

这是一种市场切入策略，不代表 OneFDE 永远只服务水果店。

## 2.2 客户需求原则

OneFDE 不应预先假定每个客户都需要同一套软件。

面对客户提出的"想提高效率""不知道哪家供应商划算""库存损耗比较大"等问题，FDE
Agent 应先了解：

-   客户当前如何完成这项工作；
-   使用哪些数据、文件和工具；
-   哪些环节最耗时或容易出错；
-   当前业务规则和判断依据是什么；
-   客户希望改善的结果是什么。

之后再决定交付一张报表、一个小工具、一条自动化流程，还是更完整的系统。

## 2.3 后续客户拓展

建议按能力积累逐步拓展：

1.  社区水果店、单体小型生鲜门店；
2.  水果批发商、供应商；
3.  有多门店管理需求的小型连锁生鲜企业。

后续拓展应以实际客户需求、已有交付经验和能力库成熟度为依据，不在首版同时覆盖所有类型。

# 3. 商业模式

OneFDE 支撑公司探索三种服务模式。

  -----------------------------------------------------------------------------------------------------------------------
  模式               客户购买什么                               OneFDE 的作用                          当前定位
  ------------------ ------------------------------------------ -------------------------------------- ------------------
  定制化解决方案     针对自身经营问题定制的软件、工具或自动化   诊断需求、制定方案、开发与交付         首阶段优先验证

  标准产品 + 定制    可复用的基础产品，以及适配自身业务的功能   复用标准模块、配置和扩展功能           能力积累后的方向

  持续经营技术服务   持续的自动化建设、系统改进和维护           读取既有项目背景，持续分析需求并迭代   后续拓展方向
  -----------------------------------------------------------------------------------------------------------------------

首版不需要同时建立三套商业体系。建议先通过定制化小型解决方案验证客户是否愿意为实际经营改善付费，再从重复出现的需求中识别标准化产品机会。

最终报价、合同、交付范围和商业承诺由创始人负责；Business Agent
可以准备分析和草案，但不自行作出未经确认的商业承诺。

# 4. 产品形态与整体结构

## 4.1 产品形态

OneFDE 采用**内部 Web 工作台**形态。

它不是单一聊天窗口，也不是面向客户开放的通用
SaaS。工作台围绕公司经营、客户项目、工程执行和能力沉淀组织信息。

客户首版不需要登录
OneFDE。客户通过公司交付的独立软件、网页工具或自动化入口使用成果。

## 4.2 工作台模块

建议首版工作台采用以下四个主要模块。

  ------------------------------------------------------------------------------------------------
  模块                    服务对象                主要职责
  ----------------------- ----------------------- ------------------------------------------------
  经营中心                OPC 创始人、Business    市场研究、客户线索、营销材料、商机跟进
                          Agent                   

  客户项目                创始人、FDE Agent       Engagement、客户背景、需求证据、方案和工程任务

  工程工作区              创始人、Engineering     工程任务、项目文件、执行记录、构建与部署结果
                          Agent                   

  能力中心                创始人、FDE             Capability Library 的检索、整理、查看和复用
                          Agent、Knowledge Agent  
  ------------------------------------------------------------------------------------------------

以上是产品信息架构建议，不等于首版必须实现完整 CRM、IDE
或复杂知识管理系统。界面和功能深度应围绕跑通首个交付闭环确定。

## 4.3 整体协作关系

创始人统筹公司经营和关键决策。Business Agent 服务公司经营；FDE Agent
是客户交付核心；Engineering Agent 按 FDE 的任务执行工程工作；Knowledge
Agent 在交付和反馈等节点提炼资产。

四个 Agent 不是四个平级部门，也不是每个项目都必须同时运行。

``` text
                         OPC 创始人
                经营方向 / 客户关系 / 关键决策
                           |
             +-------------+-------------+
             |                           |
       Business Agent               FDE Agent
       公司经营与获客               客户交付核心
             |                           |
        客户线索 -----------------> Engagement
                                         |
                                  方案与工程任务
                                         |
                                  Engineering Agent
                                  真实工程执行
                                         |
                                  软件 / 构建 / 部署
                                         |
                                   客户使用与反馈
                                         |
                                  Knowledge Agent
                                  反馈与资产提炼
                                         |
                                  Capability Library
                                         |
                                  下一次项目复用
```

# 5. Agent 团队定义

## 5.1 Business Agent｜公司经营与增长

### 定位

服务 OPC
自己，帮助创始人发现商机、表达服务价值并跟进潜在客户。它不是客户项目的技术实施负责人。

### 核心职责

-   **市场研究**：研究生鲜行业的经营流程、常见痛点和可切入场景。
-   **客户线索**：整理潜在门店、客户特征和可能存在的需求线索。
-   **营销内容**：准备案例介绍、服务说明、公众号文章、宣传素材和演示材料。
-   **销售支持**：整理客户沟通信息，生成客户情况摘要、问题假设和报价草案。
-   **客户跟进**：记录商机状态、整理反馈并提出下一步沟通建议。

### 主要输入

-   公司服务定位和目标客户画像；
-   市场信息、公开资料和调研记录；
-   创始人提供的客户沟通记录；
-   已交付案例和可公开展示的成果。

### 主要输出

-   潜在客户线索；
-   客户需求线索和商机摘要；
-   营销内容与销售材料；
-   客户跟进建议；
-   报价或服务方案草案。

### 职责边界

Business Agent
可以研究、准备和建议，但不自行确定最终报价、合同条款或对客户作出未经创始人确认的商业承诺。客户进入实际交付后，相关业务资料可整理进入对应
Engagement。

## 5.2 FDE Agent｜客户项目与解决方案负责人

### 定位

OneFDE
的客户交付核心。它将客户模糊的经营诉求转化为有依据、可实施的解决方案，并组织
Engineering Agent 完成工程工作。

### 核心职责

1.  **业务访谈**：主动追问客户的工作流程、数据来源、业务规则和实际困难。
2.  **证据整理**：关联客户提供的文件、样例、记录和访谈结论，区分事实、假设与未知信息。
3.  **问题诊断**：识别客户真正需要改善的环节，而不是直接把客户原话转换成开发任务。
4.  **方案制定**：明确目标、范围、输入、输出、业务规则和限制。
5.  **能力检索**：从 Capability Library
    查找适用的行业知识、业务模块和工程经验。
6.  **交付策略选择**：判断直接复用、组合扩展或局部全新开发。
7.  **工程任务拆解**：将方案拆成可执行、可检查的工程任务。
8.  **交付推进**：跟踪工程执行结果，处理需求与实现之间的偏差，并向创始人说明关键取舍。

### 主要输入

-   Engagement 中的客户背景和需求资料；
-   客户提供的文件、数据样例和业务规则；
-   Capability Library 中的相关能力；
-   创始人的业务方向和范围决策。

### 主要输出

-   需求与业务问题说明；
-   证据和待确认信息清单；
-   解决方案及范围；
-   复用、组合或开发的决策说明；
-   Engineering Task；
-   对工程结果的业务层判断和交付说明。

### 职责边界

-   不擅自扩大客户已确认的业务范围；
-   不把未经验证的业务假设当成事实；
-   不要求 Engineering Agent 对模糊规格自行猜测；
-   对价格、合同、重大范围变化等商业决策向创始人提出建议，由创始人决定。

## 5.3 Engineering Agent｜软件工程执行者

### 定位

把 FDE Agent
制定的方案和工程任务转化为真正可运行、可访问的软件，而不只是生成代码片段。

### 核心职责

-   创建和管理项目工程工作区；
-   读取、创建和修改项目文件；
-   安装依赖、执行命令和调用开发工具；
-   按任务实现前端、后端、数据处理和必要集成；
-   分析日志、定位错误并修复问题；
-   执行必要的构建和基础测试；
-   启动应用并检查核心功能；
-   将应用部署到目标环境；
-   返回源代码、构建结果、部署地址和必要说明。

### 主要输入

-   FDE 提供的工程任务；
-   客户授权提供的脱敏样例数据；
-   适用的 Capability Library 资产；
-   工程环境、项目模板和部署配置。

### 主要输出

-   源代码和项目文件；
-   配置及必要的数据处理逻辑；
-   构建与运行结果；
-   基础测试或启动检查结果；
-   可访问的预览或部署地址；
-   工程执行摘要和已知限制。

### 工程执行要求

1.  工程任务应明确目标、输入、输出和完成条件。
2.  代码编辑、命令执行、文件访问和应用运行由工程工具实际完成，不能把模型生成的文字描述当作执行成功。
3.  工程 Agent
    应在隔离的工程工作区中工作，避免不同客户项目之间的文件和数据混用。
4.  开发完成后至少完成必要的构建、启动和核心功能检查。
5.  部署成功必须有真实结果和可访问入口作为依据，不能仅凭生成的部署说明声称已上线。

### 职责边界

-   不替客户决定业务规则；
-   不对规格不明的数据自行作出业务推断；
-   不擅自扩大 FDE 确定的工程范围；
-   不将一个客户的原始数据带入其他客户项目；
-   对无法完成的任务、环境限制和已知问题如实反馈。

## 5.4 Knowledge Agent｜知识与资产沉淀

### 定位

从客户项目、交付结果和使用反馈中提取可复用的行业知识、业务模块和工程经验，让每次交付都能为下一次交付积累能力。

Knowledge Agent
不是简单的聊天记录总结器，也不只是把文件放进知识库。它需要识别哪些内容具有跨项目复用价值，并整理其来源、适用条件和限制。

### 核心职责

1.  **反馈分析**：整理客户使用反馈，识别已解决问题、未解决问题和新增需求。
2.  **行业知识提炼**：提取商品规格、计量单位、采购规则等可泛化的业务知识。
3.  **业务模块沉淀**：识别可复用的数据处理、业务逻辑、页面组件和自动化模块。
4.  **工程经验沉淀**：整理常见文件兼容、异常处理、调试、构建和部署经验。
5.  **资产整理**：为资产补充来源、适用条件、输入输出、限制和验证状态。
6.  **复用支持**：使 FDE 能够检索已有能力，判断是否适用于新客户。

### 触发时机

首版可采用事件或人工触发，不要求 Agent 常驻运行。典型触发包括：

-   一个客户项目完成主要交付；
-   客户提交新的使用反馈；
-   Engineering Agent 完成具有复用价值的模块；
-   FDE 发现新的行业业务规则或解决方案；
-   创始人要求整理某个项目的经验。

### 主要输入

-   Engagement 中的需求、业务规则、工程结果和交付记录；
-   客户使用反馈；
-   已有 Capability Library 资产；
-   创始人对可复用范围的说明。

### 主要输出

-   行业知识条目；
-   可复用业务模块；
-   工程经验条目；
-   已有资产的改进建议；
-   后续项目可参考的交付案例和复用建议。

### 数据与复用边界

-   客户原始文件、客户专属代码、个人信息和商业机密不能因为进入项目就自动成为公共资产。
-   跨客户复用应针对经过整理的通用知识、通用模块和工程经验。
-   每项资产应保留来源、适用条件、限制和验证状态。
-   无法确认是否可以复用的内容应保留在原客户项目范围内，不进入跨项目通用资产。

# 6. 核心业务对象

OneFDE 首版围绕两个核心对象组织业务信息：Engagement 和 Capability
Library。

## 6.1 Engagement｜客户交付项目

### 定义

Engagement
是围绕一个客户及其具体交付目标建立的项目对象，是客户背景、需求证据、方案、工程任务和交付结果的统一上下文。

它不是简单的聊天会话，也不等同于客户档案。

### 主要内容

  信息类别     说明
  ------------ ----------------------------------------
  客户背景     客户基本情况、经营场景、沟通信息
  需求与证据   客户诉求、访谈记录、文件样例、业务规则
  问题诊断     当前流程、问题判断、证据和未知信息
  解决方案     目标、范围、功能、输入输出和限制
  工程任务     任务描述、执行状态、关联代码和执行记录
  交付成果     源代码、构建产物、部署地址和使用说明
  客户反馈     使用情况、问题、改进意见和后续机会
  沉淀关联     从项目中提炼的 Capability Library 资产

### 项目生命周期（建议）

``` text
商机线索
   |
建立 Engagement
   |
业务访谈与资料收集
   |
需求诊断与方案制定
   |
工程任务拆解
   |
开发 / 调试 / 构建 / 部署
   |
客户使用与反馈
   |
经验与能力沉淀
   |
后续扩展或结束
```

生命周期用于组织项目工作，不意味着首版必须建设复杂的审批状态机。

## 6.2 Capability Library｜业务能力库

### 定义

Capability Library
是跨项目复用的能力资产集合。它不仅保存代码，还描述这些能力能够解决什么业务问题、在什么条件下适用，以及如何被
FDE 和 Engineering Agent 使用。

### 三类核心资产

  ----------------------------------------------------------------------------------------------
  资产类型                内容示例                                       主要使用者
  ----------------------- ---------------------------------------------- -----------------------
  行业业务知识            商品等级、包装规格、单位换算、报价可比条件     FDE Agent

  可复用业务模块          Excel                                          FDE Agent、Engineering
                          解析、字段映射、订单汇总、报价比较、库存预警   Agent

  工程与交付经验          文件兼容、异常处理、项目模板、构建部署经验     FDE Agent、Engineering
                                                                         Agent
  ----------------------------------------------------------------------------------------------

### 能力条目建议字段

  字段         说明
  ------------ ----------------------------------
  名称与描述   能力叫什么，解决什么问题
  资产类型     行业知识、业务模块或工程经验
  适用场景     哪类客户、业务和任务适用
  前置条件     所需数据、环境、规则和依赖
  输入与输出   使用能力需要提供什么，能得到什么
  业务规则     能力内部使用的规则和判断条件
  限制与异常   不适用情况、已知问题和边界
  关联实现     代码仓库、模块、模板或文档位置
  来源         来源 Engagement、资料或工程任务
  验证状态     草稿、已验证、限制使用或已弃用
  版本信息     版本、更新时间和变更说明
  复用范围     通用资产、受限资产或客户专属资产

### 复用流程

1.  FDE 根据客户问题检索能力库。
2.  判断已有能力的适用条件是否满足。
3.  选择直接复用、组合扩展或局部新开发。
4.  Engineering Agent 根据任务复用或适配工程模块。
5.  项目完成后，Knowledge Agent 分析是否产生了新的通用资产。
6.  更新能力库，并保留来源和验证状态。

### 资产状态建议

-   **草稿**：刚提取，尚未充分验证。
-   **已验证**：在明确场景中验证过，可以按适用条件复用。
-   **限制使用**：存在已知限制，只能在指定条件下使用。
-   **已弃用**：不再推荐使用，保留历史记录以便追溯。

能力库不应把所有项目产物自动标记为可复用资产。

# 7. 端到端业务流程

## 7.1 总体流程

``` text
客户线索
   |
Business Agent：市场研究、客户发现、销售支持
   |
创始人与客户沟通
   |
建立 Engagement
   |
FDE Agent：访谈、证据整理、业务诊断
   |
FDE Agent：制定方案、检索能力库
   |
判断交付策略
   |
   +---- 直接复用已有能力
   |
   +---- 组合与扩展已有模块
   |
   +---- 局部全新开发
   |
FDE Agent：拆解 Engineering Task
   |
Engineering Agent：真实开发与调试
   |
构建 / 启动检查 / 基础测试
   |
部署可访问的软件
   |
客户实际使用与反馈
   |
Knowledge Agent：提炼知识、模块和经验
   |
Capability Library 更新
   |
下一次项目检索和复用
```

## 7.2 三种交付策略

三种策略属于同一个 FDE 交付系统的选择，不是三套独立产品。

### 模式 A：直接复用

客户需求与已有能力高度匹配。

FDE 检索已有模块，确认适用条件后进行必要配置，尽量不调用 Coding Agent
从头开发。

### 模式 B：组合与扩展

客户已有部分能力，但需要连接、适配或补充功能。

FDE 选择已有模块，Engineering Agent 开发缺失的连接部分或客户特有逻辑。

### 模式 C：局部全新开发

没有合适的现成能力，或现有能力无法满足客户的关键需求。

FDE 先明确需求、范围和工程任务，再由 Engineering Agent
在隔离工作区开发。首版优先支持范围清晰的小型软件，不追求复杂企业系统的全自动交付。

## 7.3 反馈与持续服务

客户使用交付成果后，可能提出新的问题或扩展需求。

FDE 应读取已有 Engagement，理解既有方案和软件结构，判断新需求属于：

-   修复或改进现有功能；
-   复用已有模块增加能力；
-   新增业务模块；
-   需要重新讨论的业务范围。

不应每次都重新建立客户背景或从零开发。

# 8. 首个贯穿案例：水果店供应商报价比较

## 8.1 客户场景

水果店老板每天从不同供应商采购水果。各供应商报价格式不一致，同一种水果的等级、包装和计量单位也可能不同。老板需要人工整理报价，难以快速判断哪家真正划算。

客户原话示例：

> 我每天从不同供应商那里进水果，报价很乱，经常不知道哪家真正划算。

## 8.2 首版目标

交付一个可使用的供应商报价比较工具，帮助老板：

-   导入多家供应商报价文件；
-   整理商品和报价信息；
-   对可比较商品统一计量口径；
-   计算并展示可比较的单位价格；
-   标记规格不明、信息缺失或不可直接比较的项目；
-   查看和导出比较结果。

首版不承诺自动采购，也不直接替老板决定采购哪一家。

## 8.3 FDE 需要了解的信息

  访谈主题   需要确认的问题
  ---------- -------------------------------------------------
  报价来源   供应商能否提供 Excel 或 CSV？文件格式是否稳定？
  商品口径   商品品种、等级、包装、净重和计量单位是否明确？
  计量规则   斤、公斤、箱、盒等单位如何换算？
  采购条件   运费、起订量、送货日期是否影响实际成本？
  比较规则   哪些商品满足可比条件？哪些必须人工核对？
  输出方式   老板希望查看网页结果、下载表格还是两者都需要？

首版优先处理结构化的 Excel / CSV
文件。图片、微信聊天记录等非结构化来源暂不纳入首版范围。

## 8.4 业务规则

**只有商品规格和计量口径满足可比条件，系统才进行价格比较。**

例如：

  商品                          供应商 A   供应商 B 系统判断
  --------------------------- ---------- ---------- ------------------
  一级苹果（同规格，元/斤）        ¥5.00      ¥4.60 B 较低
  香蕉（同规格，元/斤）            ¥3.20      ¥3.50 A 较低
  草莓（盒装，净重未知）        ¥18 / 盒   ¥20 / 盒 规格不明，待核对

不能仅因为某个报价的数字更低，就认定它更划算。规格、等级、净重或单位信息不足时，应标记待核对，而不是猜测。

运费、起订量和送货日期是否纳入首版计算，需要根据真实客户访谈确定。若首版不处理，应明确展示其不在当前比较结果中的影响。

## 8.5 Agent 协作

  ------------------------------------------------------------------------------------------------
  步骤              负责人              工作                                     产出
  ----------------- ------------------- ---------------------------------------- -----------------
  发现客户          Business Agent      识别水果店报价整理需求                   客户线索

  访谈诊断          FDE Agent           了解报价文件、商品规格和采购规则         需求与证据

  制定方案          FDE Agent           检索能力库，明确首版范围                 解决方案

  工程实施          Engineering Agent   解析文件、处理规格、比较价格、开发页面   可运行工具

  部署交付          Engineering Agent   构建并部署应用                           可访问地址

  使用反馈          客户、创始人、FDE   收集实际使用问题和新需求                 反馈记录

  资产沉淀          Knowledge Agent     提炼通用规则、模块和经验                 Capability
                                                                                 Library 资产

  再次复用          FDE、Engineering    在新客户项目中检索和适配                 更快的交付
  ------------------------------------------------------------------------------------------------

## 8.6 预期沉淀资产

-   Excel / CSV 报价解析模块；
-   供应商字段映射能力；
-   商品规格和计量单位转换规则；
-   单位价格比较逻辑；
-   不可比较项和异常数据标记能力；
-   报价比较页面模板；
-   文件兼容、异常处理和部署经验。

这些资产必须经过整理，并明确适用条件和限制。客户的原始报价文件不能直接作为其他客户的输入或公共资产。

# 9. MVP 范围与非目标

## 9.1 MVP 的核心目标

首版的目标不是建设一个功能齐全的企业管理平台，而是验证：

**一个人能否借助四个 Agent，通过 OneFDE
获得客户需求，并将其转化为真正可访问的软件，完成一次交付，再把经验沉淀为下一次可复用的能力。**

## 9.2 MVP 必须具备的能力

  模块              MVP 必须具备
  ----------------- -----------------------------------------------------
  经营中心          能辅助整理客户线索、准备营销和销售材料
  客户项目          能创建和查看 Engagement，保存需求、证据、方案和任务
  FDE Agent         能分析需求、制定方案、检索能力并拆解工程任务
  工程工作区        能真实编辑文件、执行命令、调试和构建
  部署交付          至少能将首个工具部署为客户可访问的软件
  能力中心          能保存和检索行业知识、业务模块、工程经验
  Knowledge Agent   能从交付和反馈中提炼候选资产，并整理来源和限制

首版不要求所有功能都高度自动化。允许创始人在必要环节参与，但不能用人工手工完成全部工程工作来替代
Engineering Agent 的真实执行。

## 9.3 首个案例的 MVP 范围

**纳入：**

-   Excel / CSV 报价文件导入；
-   商品、供应商和报价字段解析；
-   已确认规则下的单位换算；
-   满足可比条件的单位价格比较；
-   缺失信息和不可比较项标记；
-   结果页面展示；
-   必要的结果导出；
-   构建、启动检查和部署。

**暂不纳入：**

-   自动读取微信群消息；
-   图片、语音和复杂非结构化报价识别；
-   自动向供应商询价或下单；
-   完整采购管理系统；
-   完整库存和临期促销系统；
-   POS / ERP 深度集成；
-   多门店统一管理；
-   复杂财务核算。

## 9.4 明确不建设的复杂机制

首版不建设：

-   独立 QA Agent；
-   复杂测试、审批和客户验收工作流；
-   多 Agent 自主协商组织；
-   大型企业级 CRM；
-   完整 ERP；
-   庞大的行业知识图谱；
-   全自动经营和无人监督的商业决策。

但不建设独立 QA Agent，不代表不做基本质量检查。Engineering Agent
仍需执行必要的构建、启动和核心功能检查；无法确认的业务数据必须明确标记。

# 10. 关键产品原则

1.  **业务问题优先**：先理解客户怎么经营，再决定交付什么软件。
2.  **真实交付优先**：工程执行必须产生真实代码、运行结果和可访问的软件，而不是只生成开发计划。
3.  **复用优先**：先检索能力库，再决定直接复用、组合扩展或局部开发。
4.  **Agent 按需协作**：每个 Agent 有明确职责，不为追求数量而增加角色。
5.  **项目上下文统一**：客户需求、工程任务和交付成果围绕 Engagement
    组织。
6.  **资产有来源和边界**：知识与模块必须保留来源、适用条件、限制和复用范围。
7.  **客户数据隔离**：不同客户的原始数据和专属资料不得直接跨项目复用。
8.  **创始人负责关键决策**：Agent
    提供分析和执行能力，商业方向、客户承诺和关键取舍由创始人负责。
9.  **先跑通再增强**：首版聚焦一条真实交付链路，不提前建设大型企业系统。

# 11. 成功标准

首版是否成功，不以 Agent
数量、页面数量或自动化程度衡量，而以真实业务闭环衡量。

  维度         成功表现
  ------------ ------------------------------------------------------
  获客         能发现并整理真实潜在客户及需求线索
  需求理解     FDE 能把客户模糊诉求整理为有证据的需求和方案
  工程执行     Engineering Agent 能根据任务真实修改项目并完成构建
  软件交付     至少一个真实可访问的软件工具成功部署
  业务有效性   工具能处理约定的样例数据，符合已确认业务规则
  反馈获取     能记录客户实际使用反馈和后续需求
  经验沉淀     Knowledge Agent 能形成有来源、适用条件和限制的资产
  再次复用     第二次类似需求能检索并复用已有能力，而非完全从零开始

建议比赛演示至少呈现一次完整链路：客户问题、FDE
诊断、工程任务、真实软件生成、部署访问、客户反馈和能力沉淀。

若暂时没有真实付费客户，应明确区分真实客户试点、模拟数据演示和假设性结果，不将模拟交易描述为真实收入。

# 12. 待确认事项与技术决策

以下事项目前不应被视为已确认的产品决策。

## 12.1 产品与业务待确认

  事项           当前状态   需要确认的内容
  -------------- ---------- --------------------------------------------
  首个试点客户   待确认     是否已有愿意提供真实报价文件并试用的水果店
  报价文件样式   待确认     实际 Excel / CSV 格式和字段差异
  商品规格规则   待确认     等级、包装、净重、单位换算规则
  采购条件       待确认     运费、起订量、送货时间是否纳入首版
  结果导出       产品建议   是否需要 Excel / CSV 下载及具体格式
  收费方式       待确认     首单按项目收费、按功能收费或其他方式
  客户后续服务   待确认     是否提供持续维护和迭代服务

## 12.2 技术选型待确认

已有材料中提到的 OpenHands SDK、E2B、GitHub、Vercel
等属于候选参考，不代表已经完成技术选型。

  技术领域       待决策内容
  -------------- -----------------------------------------------
  Agent 模型     MiMo 模型接入方式、工具调用和上下文管理
  Agent 编排     使用何种框架或自定义运行机制
  工程执行       OpenHands SDK 或其他 Coding Agent 执行方案
  沙盒           是否使用 E2B 或其他隔离工作区方案
  代码管理       GitHub 仓库、分支和项目模板策略
  部署           Vercel 或其他部署平台；预览与生产环境如何区分
  后端与数据库   服务端框架、数据库和文件存储
  认证与密钥     创始人登录、客户项目隔离、部署凭据管理
  资产检索       结构化元数据、全文检索或向量检索的组合方式
  运行成本       模型调用、沙盒、存储和部署成本

技术选择应围绕首版的真实交付需求进行验证，不应为了使用某个框架或服务而增加不必要的产品复杂度。

## 12.3 发布与操作边界待确认

-   Engineering Agent 在开发、预览和生产环境分别拥有何种执行权限；
-   哪些部署操作可自动执行，哪些需要创始人介入；
-   客户项目的代码、文件、凭据和运行环境如何隔离；
-   客户数据保存期限、删除方式和备份策略；
-   资产从项目资料转化为跨项目通用能力的具体规则。

这些事项需要在工程设计阶段明确，但首版不需要因此建设复杂的企业审批体系。

# 13. 后续实施建议

产品定义确认后，建议按以下顺序推进：

1.  **产品与真实需求准备**：找到首个试点客户，收集脱敏报价样例，确认商品规格和比较规则。
2.  **OneFDE 工作台基础**：建立内部登录、经营中心、Engagement
    和基本项目资料管理。
3.  **Agent 核心链路**：接入 Business、FDE、Engineering、Knowledge
    四个角色，打通必要的任务和上下文传递。
4.  **工程执行能力**：完成隔离工作区、文件操作、命令执行、调试、构建和基础检查。
5.  **真实部署能力**：完成首个报价比较工具的部署，提供客户可访问入口。
6.  **能力库基础**：建立资产分类、元数据、来源、适用条件、验证状态和检索能力。
7.  **完整案例演示**：以供应商报价比较为贯穿案例，演示从客户问题到软件交付和资产复用的闭环。
8.  **第二次复用验证**：使用第二组客户样例或明确标注的模拟客户数据，验证能力库是否能减少重复开发。

实施顺序可以根据真实客户资料和工程风险调整，但不应跳过真实软件生成与部署这一核心验证。
