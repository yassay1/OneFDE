# Engagement 记录约定

Engagement 围绕一个客户及其具体交付目标保存持续上下文。它应使创始人、FDE 和后续执行会话能够回答：要解决什么问题、依据什么、哪些已确认、目前交付到哪里、接下来需要什么。

平台需求见 [PRD](../docs/product/PRD.md)。本目录记录具体项目，不重复维护平台全部产品需求。

## 最小记录方式

首版可在 `<engagement-id>/brief.md` 中维护一份记录；内容增多后再按证据、任务或交付拆分。目录是文档组织约定，不代表运行时持久化方案已确定。

一份记录至少包含：

| 内容 | 记录要求 |
| --- | --- |
| 身份与目标 | 稳定项目 ID、客户或模拟标记、当前目标与范围 |
| 来源与证据 | 文件或访谈引用、时间、来源身份和可用范围；资料不可访问时写明限制 |
| 规则与未知项 | 每条规则区分已确认、建议和待确认；记录确认依据及修订 |
| 诊断与方案 | 当前问题、预期结果、输入输出、限制与选择理由 |
| 能力策略 | 检索候选、适用条件、所用版本，以及直接复用/组合/新开发理由 |
| 任务与运行 | 任务目标、前置产物、完成条件；关联执行尝试、Session/工作区及结果引用 |
| 交付与反馈 | 代码或产物版本、实际访问入口、检查结果、已知限制和反馈来源 |
| 资产关联 | 提炼出的候选能力及复用范围，不直接公开客户原始资料 |

没有资料或结果时写“尚未提供”或“未执行”，不要填入虚构的客户反馈、部署地址或成功结论。

## 任务交接

FDE 在派工前明确任务归属、目标、已确认业务规则、输入引用、前置产物、预期输出和完成条件。一个 Engagement 可有多个任务；一个任务可有多次运行。模型对话 Session 只是执行上下文，不是项目状态的唯一依据。

执行结果回填实际产物与检查依据。业务问题、回答与修改默认保存在原 Task 的输入记录；运行结束不关闭持续工作，FDE/创始人评审固定提交后才完成。已关闭后的后续工作关联原 Task、代码和产物。权威契约见[数据模型](../docs/architecture/data-model.md)，本约定只维护交付资料组织。

项目内共享资料通过相关引用提供；不要把全部项目对话自动发送给每个任务。规则变化由 FDE 判断影响，并更新相关任务的输入版本。

## 客户资料边界

真实客户文件、个人信息、客户专属代码和凭据留在受控范围，不直接提交到共享仓库。项目记录可使用受控引用；引用本身也应避免暴露敏感内容。演示数据明确标注为模拟，不能据此宣称真实经营收益。

知识与实现进入跨项目能力库前，先确认可复用范围并整理来源、条件和验证依据；不确定能否复用的内容留在原项目。资产记录方式见[能力库约定](../capability-library/README.md)。

Knowledge 可以按实际调用方和用途授权读取本项目资料，原始证据仍留在 Engagement；答复或摘要不自动成为通用资产。提供给 Business 的案例/交付说明使用明确获准的版本或视图，内部可读不等于可对外展示。Business 的一般经营咨询不必另建一个客户 Engagement。

## 维护责任

FDE 维护目标、规则与方案；Engineering 回填任务产物及运行证据；Knowledge 维护候选资产关联；创始人确认关键业务取舍。由同一人协助维护这些记录也可以，不需要另建审批流。

首个示例见[报价比较演示记录](demo-supplier-quotes/brief.md)。
